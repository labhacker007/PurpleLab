# PurpleLab QA Master Strategy

**Version:** 1.0 | **Date:** 2026-07-26 | **Stack:** FastAPI + SQLAlchemy async + PostgreSQL 5434 + Redis + Celery

---

## 1. Introduction and Scope

PurpleLab is a cybersecurity simulation platform designed to run realistic attack scenarios, validate detections in the form of Sigma rules and SIEM queries, and push simulation results back to the Joti Threat Intelligence Platform. It exposes four vendor API facades (Splunk, CrowdStrike, XSIAM/Palo Alto, Microsoft Defender) so that Joti's SOAR playbooks can be tested against a fully instrumented environment without touching production systems.

This document defines the end-to-end quality assurance strategy for PurpleLab. It covers all layers of the test pyramid, the risk register that drives test priority decisions, CI/CD integration gates, fixture and factory patterns, and test data management. Every section maps directly to the actual codebase located at `c:\Projects\purplelab\backend`.

### 1.1 Primary Quality Goals

- **Correctness of state machines.** The EDR state machine in `backend/engine/edr_state_machine.py` must transition precisely according to defined triggers. Secondary events emitted on each transition must be structurally valid and vendor-formatted correctly.
- **Vendor API contract fidelity.** All four vendor simulation APIs must return responses that are structurally identical to the real vendor APIs so that Joti connectors do not require any conditionals distinguishing simulation from production.
- **Session isolation.** Concurrent simulation sessions must never share state. The in-memory registries in `edr_state_machine._machines` and `session_manager` are keyed by `session_id` (UUID); leakage between sessions would cause false pass/fail results in detection validation.
- **Joti push reliability.** On session stop, `joti.push_simulation_result()` is called. Failure is non-fatal (caught and logged at debug level) but must be monitored. QA must confirm the push path is exercised and that failures are surfaced in metrics.
- **Use case run lifecycle.** A `UseCaseRun` created with `status="pending"` must always reach a terminal state (`passed/failed/partial/error`). Celery task failures that leave rows in `pending` permanently are a defect class.
- **Deterministic ITDR dispatch.** When `dry_run=False` is sent to `/v2/itdr/scenarios/{id}/simulate`, the scenario must create a simulation session and execute fully — no partial execution or silent drop.

### 1.2 Scope Boundaries

**In scope:**
- All routes under `backend/api/v2/` including sessions, use_cases, itdr, and joti webhook
- Engine modules: `edr_state_machine`, `action_executor`, `session_manager`
- Joti integration client (`joti/client.py`) and webhook receiver (`joti/webhook.py`)
- Database model correctness (migration-level and ORM-level)
- All four vendor API simulation modules

**Out of scope:**
- Frontend React components (separate QA track)
- PurpleLab network reachability from the Joti platform (handled by integration environment tests)
- Performance benchmarks for SecureBERT (separate ML QA)

### 1.3 Document Conventions

- `UC` = Use Case
- `SM` = State Machine (EDR state machine unless qualified)
- `SSE` = Server-Sent Events (the `/events/stream` endpoint)
- `Joti push` = `push_simulation_result()` call at session stop
- Risk IDs use the format `RISK-NNN`
- Test IDs use the format `T-<layer>-<sequence>` where layer is `UNIT`, `INT`, `SYS`, or `E2E`

## 2. QA Engineer Personas

### 2.1 Security Test Engineer

**Focus:** Correctness of attack simulation semantics and detection validation logic.

**Core responsibilities:**
- Verify that each ITDR scenario (kerberoasting, pass-the-hash, golden ticket, DCSync, MFA fatigue, impossible travel, password spray, credential stuffing, token theft, privileged account creation) generates events matching the documented MITRE technique IDs.
- Validate that EDR state machine transitions are triggered only by the correct technique IDs or source types (`crowdstrike`, `crowdstrike_edr`, `edr`).
- Confirm that secondary events generated on state transitions carry correct Windows Event IDs (4719 at AT_RISK, 4688 at COMPROMISED, 7045 at ISOLATED, 1102 at REMEDIATED) and match the vendor payload schema expected by Joti.
- Verify that Sigma rules returned by `/v2/itdr/scenarios/{id}/sigma` are syntactically valid YAML and contain correct `detection` and `logsource` fields.
- Test that SPL and KQL hunt queries returned by `/v2/itdr/scenarios/{id}/hunt-queries` are parseable and reference fields present in the event payloads generated by the same scenario.
- Own the SOAR action executor test suite: verify all 11 actions (`block_ioc`, `unblock_ioc`, `isolate_host`, `release_host`, `disable_account`, `enable_account`, `reset_password`, `kill_process`, `quarantine_file`, `deploy_detection`, `inject_alert`) produce correct state changes and generate well-structured audit events in `response_actions`.

**Tooling:** pytest + httpx async test client, YAML schema validators (pyyaml + jsonschema), SPL/KQL syntax checkers.

### 2.2 Integration Test Engineer

**Focus:** API contract between PurpleLab vendor emulation and Joti connectors.

**Core responsibilities:**
- Maintain the vendor API contract test suite. For each of the four vendor APIs (Splunk, CrowdStrike, XSIAM, Defender), assert that every response field name and type matches the real vendor OpenAPI specification.
- Test the Joti webhook receiver (`POST /joti/audit-events` and `POST /joti/webhook/alerts`) end-to-end with realistic Joti payloads.
- Own the MCP ingest workflow: verify `POST /sessions/{id}/resolve-mcp` sends a correct JSON-RPC `tools/call` payload, extracts technique IDs from multiple response shapes (list vs `{events: [...]}` vs `{alerts: [...]}`), and updates the session config with `resolved_technique_ids`.
- Validate CrowdStrike OAuth2 token endpoint always returns a correctly-shaped fake token without database interaction.
- Verify SPL search results from the Splunk simulation API query the `generated_events` table correctly, filtering by `product_type` when `sourcetype=` is present in the SPL query string.
- Test the session stop → Joti push integration with a mock JotiClient to confirm the push includes `session_name`, `technique_ids`, `events_generated`, and a `summary` field.

**Tooling:** httpx TestClient, pytest-asyncio, respx for mocking external HTTP calls, Wiremock or respx stubs for Joti API responses.

### 2.3 Performance Engineer

**Focus:** Throughput, latency, and stability under concurrent load.

**Core responsibilities:**
- Benchmark SSE event streaming (`GET /sessions/{id}/events/stream`) under concurrent session counts. The SSE generator polls the DB every 1.5 seconds; validate that 20 concurrent streams do not degrade DB connection pool below acceptable thresholds.
- Measure event generation rate at the maximum session config of `event_count=2000`. Confirm the session manager does not leak memory between sessions.
- Profile Celery task queue drain time when `POST /use-cases/run-all` is triggered with 50+ active use cases. Confirm task completion time stays under 5 minutes for a single worker.
- Load test the CrowdStrike isolation endpoint (`POST /api/vendor/crowdstrike/devices/actions/v2`) at 100 requests/second to confirm the in-memory EDR state machine registry does not cause lock contention.
- Stress test the XQL query result endpoint under simultaneous sessions producing overlapping `job_id` values (RISK-009).
- Define SLOs: p95 latency for `GET /sessions/{id}/stats` must be under 200ms; SSE first-event latency must be under 3s.

**Tooling:** Locust, k6, py-spy for profiling, pgBadger for slow-query analysis.

### 2.4 Compliance Auditor

**Focus:** Audit trail completeness, data integrity, and operational security of the simulation environment.

**Core responsibilities:**
- Verify that every SOAR action executed via the action executor produces a row in `response_actions` with a non-null `session_id`, `action_type`, `actor`, `target`, `params` (JSONB), `result` (JSONB), and `created_at`.
- Confirm that the Joti webhook receiver validates `X-Joti-Token` on every request to `POST /joti/audit-events` and `POST /joti/webhook/alerts`. A missing or incorrect token must return HTTP 401, not 200.
- Audit `JotiAuditEvent` retention: events received via `POST /joti/audit-events` must be persisted with `joti_event_id`, `event_type`, `action`, `user_email`, `ip_address`, `resource_type`, `resource_id`, `correlation_id`, `details`, `created_at_joti`, and `received_at`.
- Review that ITDR scenarios do not allow `dry_run=False` without a valid active simulation session. The dispatch must create a traceable `UseCaseRun` record.
- Verify that `ContainmentAction` rows written by the `simulate-identity` endpoint include `action_type`, `target_type`, `target_value`, and `status`.
- Confirm `DeployedDetection` rows from `deploy_detection` SOAR actions include `session_id`, `name`, `sigma_yaml`, `query_spl`, `technique_ids`, `status="deployed"`, and `deployed_by`.

**Tooling:** pytest + SQLAlchemy queries against test DB, audit log diff tools, manual review checklists.

## 3. Testing Pyramid

### 3.1 Layer 1 — Unit Tests (engine and generators)

Unit tests target modules that can be exercised without a database connection or HTTP server.

**Primary targets:**

- `backend/engine/edr_state_machine.py` — `EndpointStateMachine.process_event()` for all valid and invalid transitions. Test idempotency: calling `process_event` when already in the target state returns an empty secondary-event list.
- `backend/engine/action_executor.py` — Each of the 11 action handlers in isolation using an injected mock `session_manager` and mock `edr_state_machine`. Verify `ActionResult` fields are populated correctly.
- `backend/engine/session_manager.py` — Write-through cache logic: confirm that after `start_session()`, `get_session()` returns from in-memory cache; confirm DB persistence is triggered on write.
- `backend/engine/simulation_context.py` — Simulation context builder: verify `attack_chain`, `threat_actor`, `ttps`, and `mcp_ingest` modes produce distinct non-overlapping config shapes.
- `backend/engine/generators/` — Individual event generator output: assert that each generator produces events with required fields (`product_type`, `severity`, `title`, `payload`, `target_url`, `status_code`, `success`).
- `backend/joti/client.py` — `JotiClient` methods using a respx-mocked httpx client. Test that `push_simulation_result()` returns `True` on HTTP 200 and `False` (not raise) on any exception.
- `backend/engine/ocsf_normalizer.py` — Normalization of raw events to OCSF schema. Assert required OCSF fields are always present.

**Pass criteria:** 100% line coverage on `edr_state_machine.py`, `action_executor.py`, and `joti/client.py`. Minimum 80% line coverage on all other engine modules.

### 3.2 Layer 2 — Integration Tests (vendor API contracts)

Integration tests run against a live FastAPI TestClient with a real PostgreSQL test database (schema applied via Alembic migrations on a separate `purplelab_test` schema or ephemeral Docker container).

**Primary targets:**

- **Splunk emulation:** `POST /api/vendor/splunk/services/search/jobs` creates a job in the in-memory `_jobs` dict. `GET .../jobs/{sid}` returns `dispatchState=DONE` after a configurable delay. `GET .../jobs/{sid}/results` queries `generated_events` for the session and returns hits in Splunk `results` envelope format.
- **CrowdStrike emulation:** `POST /api/vendor/crowdstrike/oauth2/token` always returns `{"access_token": "...", "token_type": "bearer", "expires_in": 1799}`. `GET /devices/v1` returns device list derived from `EndpointStateMachine.snapshot()`. `POST /devices/actions/v2` with `action_name=contain` calls `execute_action("isolate_host")` and returns a `resources` list.
- **XSIAM emulation:** `POST /public_api/v1/xql/start_xql_query` returns a `job_id`. `POST .../get_query_results` returns results for that `job_id`. Test that colliding `job_id` values do not overwrite results (RISK-009).
- **Defender emulation:** `POST /oauth2/v2.0/token` returns a fake bearer token. `GET /api/machines` returns machine list. `POST /api/machines/{id}/isolate` calls `execute_action` and returns 202.

**Pass criteria:** All vendor endpoints return HTTP 2xx. Response envelopes match documented vendor schema shape (field presence, not exact values). No cross-session data leakage in device/machine list endpoints.

### 3.3 Layer 3 — System Tests (full session lifecycle)

System tests exercise the full session lifecycle end-to-end within a single test environment.

**Primary targets:**

- Create a session with `simulation_mode="ttps"` and `technique_ids=["T1059.001", "T1003.001"]`. Start it. Poll `/sessions/{id}/events` until at least 5 events are present or a 10-second timeout. Assert events include technique IDs matching those configured.
- After event generation, verify the EDR state machine for the session has at least one endpoint in `AT_RISK` or `COMPROMISED` state (T1059 → anomaly_detected; T1003 → confirmed_detection).
- Stop the session. Assert `status="stopped"` in DB. Assert `joti.push_simulation_result()` was called (mock or spy).
- Run a use case: `POST /use-cases/{id}/run`. Poll `GET /use-cases/{id}/runs` until the run record reaches a terminal status. Assert it is not stuck in `pending` (RISK-005).
- Identity simulation: create a use case tagged `identity`, call `POST /use-cases/{id}/simulate-identity` with `action="lock_user"`. Assert a `ContainmentAction` row is written.

**Pass criteria:** All session lifecycle state transitions complete. No `pending` UseCaseRun rows remain after 60 seconds. EDR state machine state matches expected state given the technique_ids used.

### 3.4 Layer 4 — End-to-End Tests (Joti integration)

E2E tests require both PurpleLab and a Joti staging instance (or a fully-mocked Joti API) to be running.

**Primary targets:**

- **Outbound push:** Complete a simulation session. Assert that Joti's `/api/v2/simulations` endpoint receives a POST with `session_name`, `technique_ids`, `events_generated`, and `summary`. Verify the response is `200 OK`.
- **Inbound audit events:** Configure Joti's SIEM audit forwarder with `target_type=purplelab` pointing to `POST /joti/audit-events`. Perform a login action in Joti. Confirm a `JotiAuditEvent` row appears in PurpleLab's DB within 90 seconds.
- **Inbound alert webhook:** POST a synthetic alert to `POST /joti/webhook/alerts` with a technique_id matching an active use case. Assert a `UseCaseRun` is created with `triggered_by="joti_webhook"` and the correct `status` derived from the alert's `severity` (critical/high → failed, medium → partial, low/info → passed).
- **Coverage score pull:** Verify `JotiClient.get_coverage_score()` calls Joti's `/api/v2/coverage/score` and returns a dict containing `score`, `covered_techniques`, and `total_techniques`.

**Pass criteria:** All data flows complete within configured timeout. DB rows are written in PurpleLab. Joti staging reflects the simulation result. No unhandled exceptions in either direction.

## 4. Risk Register

The following 10 risks are ranked by their potential impact on test reliability and production correctness.

### RISK-001 — EDR State Machine Race Conditions

| Field | Value |
|-------|-------|
| **ID** | RISK-001 |
| **Description** | `edr_state_machine._machines` is a module-level dict shared across all async coroutines in a single process. Under concurrent event generation for different sessions, Python's async event loop serializes coroutine execution, but multiple `process_event()` calls for the same session_id could interleave between the state read (`get_state`) and the state write (`self._states[hostname] = next_state`). |
| **Likelihood** | Medium |
| **Impact** | High |
| **Mitigation** | Add a per-session `asyncio.Lock` inside `EndpointStateMachine`. Test by launching 10 concurrent `process_event()` tasks on the same hostname and asserting the final state is deterministic. Include a regression test: sequence `T1059 → T1003 → manual isolate` must always end in ISOLATED, never in AT_RISK. |

### RISK-002 — Vendor API In-Memory State Loss on Restart

| Field | Value |
|-------|-------|
| **ID** | RISK-002 |
| **Description** | The Splunk simulation API maintains `_jobs` (search job registry) and `_saved_searches` as plain Python dicts in the vendor route module. The CrowdStrike and XSIAM APIs maintain similar in-memory job/IOC registries. A container restart during an active Joti playbook run clears all registered jobs, causing the playbook to receive 404 on subsequent job status polls. |
| **Likelihood** | Medium |
| **Impact** | High |
| **Mitigation** | Add a Redis-backed job registry for the Splunk and XSIAM emulators using the existing Redis connection. QA test: start a Splunk search job, simulate process restart (re-initialize the module dict), then poll the job — confirm it returns 404 and Joti handles the error gracefully. Document this as a known limitation in the interim. |

### RISK-003 — Joti Push Failure on Session Stop

| Field | Value |
|-------|-------|
| **ID** | RISK-003 |
| **Description** | `POST /sessions/{id}/stop` calls `joti.push_simulation_result()` in the `_do_stop()` helper. Failure is caught and logged at debug level, silently discarding the simulation result. If Joti is unreachable or returns a 5xx, the session appears stopped but no Joti record exists. |
| **Likelihood** | Low |
| **Impact** | High |
| **Mitigation** | Add a `joti_push_status` column to `simulation_sessions` (`success/failed/skipped`). Write the push outcome before returning from `_do_stop()`. QA test: mock `push_simulation_result()` to return `False` and assert `joti_push_status=failed` is persisted. Add a dashboard alert in Joti for sessions with no corresponding simulation record within 5 minutes of stop time. |

### RISK-004 — Session ID Isolation Between Concurrent Sessions

| Field | Value |
|-------|-------|
| **ID** | RISK-004 |
| **Description** | All four vendor API facades (`crowdstrike`, `splunk`, `xsiam`, `defender`) look up state via `get_machine(session_id)`. If a vendor endpoint is called without a `session_id` (or with an incorrect one), the state machine returns the default `ONLINE` state for an unknown hostname. More critically, if a vendor API derives `session_id` incorrectly, a device list from session A could be returned to a client of session B. |
| **Likelihood** | Low |
| **Impact** | High |
| **Mitigation** | Integration tests must run two concurrent sessions and assert that `GET /api/vendor/crowdstrike/devices/v1?session_id=A` never returns devices only created in session B. Add `session_id` validation in vendor route handlers: return 400 if `session_id` is missing or not a valid UUID. |

### RISK-005 — Celery Task Failures Leaving UseCaseRun Stuck in Pending

| Field | Value |
|-------|-------|
| **ID** | RISK-005 |
| **Description** | `POST /use-cases/{id}/run` creates a `UseCaseRun` with `status="pending"` and then calls `run_use_case_task.delay()`. If the Celery worker is not running, crashes, or the task raises an unhandled exception before writing a terminal status, the row stays in `pending` forever. `GET /use-cases/failing` may not surface these because the query filters for use cases with no `passed` run, not for stuck `pending` runs. |
| **Likelihood** | Medium |
| **Impact** | Medium |
| **Mitigation** | Add a watchdog scheduler job (APScheduler) that queries `UseCaseRun` rows where `status="pending"` and `started_at < now() - interval '10 minutes'`, then updates them to `status="error"` with `error_message="watchdog_timeout"`. QA test: insert a fake pending run with `started_at = now() - 11 minutes`, wait for the watchdog cycle, assert it flips to `error`. |

### RISK-006 — MCP Ingest from Untrusted External Servers

| Field | Value |
|-------|-------|
| **ID** | RISK-006 |
| **Description** | `POST /sessions/{id}/resolve-mcp` sends a JSON-RPC call to an `mcp_server_url` stored in the session config. This URL is user-supplied at session creation and is not validated against an allowlist. A malicious or misconfigured `mcp_server_url` could point to an internal service (SSRF), return a malformed response that causes an unhandled exception, or return a very large payload that exhausts memory. |
| **Likelihood** | Medium |
| **Impact** | High |
| **Mitigation** | Add URL validation in `resolve-mcp`: reject `file://`, `ftp://`, and private RFC-1918 address ranges. Cap response body size at 1 MB. QA test: supply `mcp_server_url=http://169.254.169.254/latest/meta-data/` and assert 400 or 502 is returned. Supply a URL returning 10 MB of JSON and assert a 413 or safe truncation. |

### RISK-007 — ITDR Scenario Dispatch with dry_run=False

| Field | Value |
|-------|-------|
| **ID** | RISK-007 |
| **Description** | `POST /itdr/scenarios/{id}/simulate` with `dry_run=False` dispatches a real simulation session. The dispatch path calls `POST /v2/scenarios` internally. If the backend cannot create the session (DB error, malformed config), the ITDR endpoint may return 500 or silently succeed without creating a traceable session. An analyst relying on this to validate a detection would receive no audit trail. |
| **Likelihood** | Low |
| **Impact** | Medium |
| **Mitigation** | Add a response field `session_id` to the ITDR simulate endpoint. Assert in QA that every `dry_run=False` call returns a non-null `session_id` that resolves to a real row in `simulation_sessions`. Test failure modes: DB down → 503 with explicit error. Missing technique mapping → 422. |

### RISK-008 — SPL Search Against Stale Events

| Field | Value |
|-------|-------|
| **ID** | RISK-008 |
| **Description** | The Splunk simulation API runs SPL searches by querying `generated_events` in the database. If a session has been deleted (cascade delete removes `generated_events`), an in-flight Joti playbook step that polls the search job results will receive empty results and may incorrectly interpret this as no detections — producing a false negative in detection validation. |
| **Likelihood** | Medium |
| **Impact** | Medium |
| **Mitigation** | Add a session status check at SPL search creation time: if session is `stopped` and older than 24 hours, return a `Warning` header in the search results response. QA test: create a session, add events, delete session, run SPL search — assert an empty result with a warning, not a 500. |

### RISK-009 — XQL Job ID Collisions

| Field | Value |
|-------|-------|
| **ID** | RISK-009 |
| **Description** | The XSIAM emulation maintains an in-memory dict mapping `job_id` to query results. `job_id` is generated as a UUID string on each `POST .../xql/start_xql_query`. However, if the module-level registry is shared across sessions without a `session_id` prefix, two concurrent sessions running the same XQL query could receive each other's results. |
| **Likelihood** | Low |
| **Impact** | High |
| **Mitigation** | Prefix `job_id` with `{session_id}:` in the in-memory registry key. QA test: start two concurrent sessions, each running an XQL query, then poll results and assert each session receives only its own events. |

### RISK-010 — Use Case Run Status Stuck in Pending After Worker Drain

| Field | Value |
|-------|-------|
| **ID** | RISK-010 |
| **Description** | When `POST /use-cases/run-all` is called during a Celery worker scale-down event (e.g. during Docker restart), the task may be acknowledged by the worker but not executed before the worker process exits. Celery's default `acks_late=False` means the task is removed from the queue even though it was never run. The `UseCaseRun` row remains in `pending` state with no mechanism to detect or recover. |
| **Likelihood** | Low |
| **Impact** | Medium |
| **Mitigation** | Configure Celery with `task_acks_late=True` and `task_reject_on_worker_lost=True` for `run_use_case_task` and `run_all_use_cases_task`. QA test: queue 5 tasks, send SIGKILL to the worker, restart worker, confirm all tasks complete and no `pending` runs remain after 5 minutes. |

## 5. CI/CD Gates and Test Categories

### 5.1 Gate Structure

Three quality gates run in CI for every pull request:

**Gate 1 — Fast feedback (under 90 seconds)**
- `pytest tests/unit/` — all unit tests against in-memory fakes, no DB required
- `mypy backend/` — type checking
- `ruff backend/` — linting

**Gate 2 — Integration (under 8 minutes)**
- `pytest tests/integration/` with a Docker-compose test environment (PostgreSQL on 5434, Redis)
- Applies Alembic migrations to an ephemeral `purplelab_test` database before the suite runs
- Tears down the test database on completion
- Vendor API contract tests included

**Gate 3 — System (under 20 minutes, on merge to main)**
- `pytest tests/system/` — full session lifecycle, Celery worker spun up
- Joti mock server (respx stubs) used in place of the real Joti API
- E2E Joti integration tests run only against the staging environment

### 5.2 Test Category Tags

Every test is tagged with one or more of the following pytest markers:

```
@pytest.mark.unit       # Pure Python, no I/O
@pytest.mark.integration # Requires DB + Redis
@pytest.mark.system     # Requires full stack
@pytest.mark.e2e        # Requires Joti staging
@pytest.mark.vendor     # Vendor API contract tests
@pytest.mark.security   # Auth, token validation, SSRF checks
@pytest.mark.risk_001   # Maps to RISK-001 (substitute risk ID)
```

Run categories selectively:
```bash
pytest -m "unit or integration" --timeout=120
pytest -m "vendor" --timeout=60
pytest -m "security" -v
```

## 6. Factory Patterns and Fixture Design

### 6.1 Session Factory

```python
# tests/factories/session_factory.py

import uuid
from backend.db.models import SimulationSession

class SessionFactory:
    @staticmethod
    def build(
        simulation_mode: str = "ttps",
        technique_ids: list[str] | None = None,
        status: str = "stopped",
        event_count: int = 50,
    ) -> SimulationSession:
        return SimulationSession(
            id=uuid.uuid4(),
            name=f"Test Session {uuid.uuid4().hex[:8]}",
            config={
                "simulation_mode": simulation_mode,
                "technique_ids": technique_ids or ["T1059.001"],
                "event_count": event_count,
            },
            status=status,
            events_sent=0,
            errors=0,
        )

    @staticmethod
    async def create(db, **kwargs) -> SimulationSession:
        session = SessionFactory.build(**kwargs)
        db.add(session)
        await db.commit()
        await db.refresh(session)
        return session
```

### 6.4 Async Test Database Fixture

```python
@pytest.fixture(scope="session")
```

## 7. Test Data Management

### 7.1 Synthetic Event Data

Generated events are always synthetic — they are produced by the engine generators in `backend/engine/generators/` and represent simulated vendor telemetry, never real security data. Test suites must:

- Never use real IP addresses, hostnames, or credentials as test data.
- Use the `10.0.0.0/8` and `192.168.0.0/16` ranges for simulated IPs in test payloads.
- Use `WIN-TEST-001`, `WIN-TEST-002` etc. as simulated hostnames.
- Use `testuser@example.local` format for simulated user accounts in identity tests.

### 7.2 DB-Backed Test Data vs In-Memory Fixtures

Unit tests (Gate 1) must use only in-memory factories. No DB connection is permitted in unit tests. The `@pytest.mark.unit` guard enforces this by setting `DATABASE_URL=sqlite+aiosqlite:///:memory:` in the test environment, which will cause any SQL executed by a unit test to operate against SQLite.

Integration tests (Gate 2) use the real PostgreSQL test database on port 5434. The `db` fixture provides a transactional session that rolls back after each test, ensuring test isolation without the overhead of truncating tables between tests.

System tests (Gate 3) may seed the database with persistent fixtures using a `conftest.py` session-scoped setup that inserts standard use cases and cleans them up in a `teardown_session` hook.

### 7.3 ITDR Scenario Data

The ITDR scenarios catalogue is defined as a static Python list in `backend/api/v2/itdr.py`. These are not database-backed. Tests for ITDR scenarios must use the catalogue directly rather than mocking it. The canonical test for scenario existence is:

```python
def test_itdr_scenario_kerberoasting_has_sigma():
    from backend.api.v2.itdr import ITDR_SCENARIOS
    scenario = next(s for s in ITDR_SCENARIOS if s["id"] == "kerberoasting")
    assert "detection_sigma" in scenario
    assert scenario["technique_id"] == "T1558.003"
    import yaml
    parsed = yaml.safe_load(scenario["detection_sigma"])
    assert "detection" in parsed
    assert "logsource" in parsed
```

### 7.4 Joti Audit Event Samples

For integration tests that exercise the Joti audit event ingest path, use the following canonical payload shape (derived from the `JotiAuditEvent` model):

```json

  "event_type": "HUNT_TRIGGER",
  "action": "create",
  "user_email": "analyst@example.local",
  "ip_address": "10.0.0.1",
  "resource_type": "hunt",
  "resource_id": "42",
  "correlation_id": "corr-abc123",
  "details": {"technique_id": "T1059.001", "hunt_id": 42},
```

`HUNT_TRIGGER` and `EXTRACTION` are the two event types that auto-create `UseCaseRun` records. All other event types are stored without triggering any downstream action.

### 7.5 Test Data Cleanup

All tests that create DB rows must clean up after themselves or use the transactional rollback fixture. Explicitly never use `TRUNCATE` in test teardown — use `DELETE FROM table WHERE id IN (...)` scoped to the test session's created IDs, or rely on the transactional rollback fixture to undo all writes.
